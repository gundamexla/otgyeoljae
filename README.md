# 모아 · 후회 없이 사는 AI 쇼핑 결재 비서

OBA.RUN 2nd 해커톤 (2026-11-07) · SKT 트랙(모두의 AI × Agentic Pay) + 메인 트랙

## 한 줄
러프하게 말하면 캐릭터 비서 '볼티'가 저장한 착장에 상품을 붙여 제안하고, **문턱 안이면 바로 처리, 넘으면 근거와 포기한 대안을 담은 결재 서류로 올리고, 안 사는 게 이득이면 말립니다.** 구매 뒤에는 후회 체크로 문턱이 스스로 다듬어집니다.

## 왜
AI에게 구매를 맡기면 다 묻거나(귀찮음) 다 사버리거나(불안) 둘 중 하나가 됩니다. 필요한 건 "무엇을 맡기고 무엇을 내가 결재할지"를 정하는 **문턱**이고, 목표는 "후회 없이 잘 썼다"입니다.

## 메인 시연: 모아 · 면접 옷 (팀원 SB 시나리오)
1. "다음 주 면접에 입을 옷이 필요해. 이 재킷 사도 될까?" → SKT A.X K2 의도 해석 → **예산 확인**: 잔액 130,000 / 남겨둘 생활비 70,000 / 쓸 수 있는 돈 60,000 → 재킷 89,000원은 생활비 침범
2. **가진 옷 살리기**: 옷장의 검정 재킷을 활용한 착장과 새 재킷 착장을 비교 → 바지만 바꾸기로
3. **지난 구매 피드백 반영**: "드라이클리닝 번거로워서 안 입게 돼" → 물세탁 가능 바지 추천(상품 정보 출처 표시)
4. **최종 결재 카드**: 가진 것/새로 살 것/배송비/총지출 42,000/구매 후 잔액 88,000/생활비 유지/추가 사용 가능 18,000 → 승인 → 모의 결제 → 가상 잔액 반영 → 기록 저장
5. **일주일 후**: "관리는 편했는데 허리가 불편" → "바지 구매 → 허리 치수·착용 정보 확인 필요"를 사용자가 설정에 추가

> 모아는 옷을 대신 사주는 데서 끝나지 않습니다. 가진 옷과 남겨둘 돈, 지난 구매의 아쉬움까지 연결해 필요한 선택을 돕습니다.

팀: 허우민(익뇽), SB (LSB04)

## 추가 데모: 결혼식 하객룩
1. **"이번 주말 결혼식 가는데 뭐 입지"** → SKT A.X K2가 의도를 JSON으로 해석(캘린더 11/8 결혼식, 옷장 근거) → 하객룩 A 제안
2. 옷장에 이미 있는 **흰 셔츠는 "안 사는 게 이득"** 으로 빼고 총액 재계산
3. 총액 19만원(기준 10만원 이상) + 환불 불가 상품 → **결재 서류**: 무엇을/왜(규칙)/근거(출처 표시)/포기한 대안(문턱 안인 하객룩 B)/잘못되면 수습
4. 승인 → **시뮬레이션 결제** 영수증 (중복 클릭 방지)
5. **"일주일 후"** → 후회 체크에서 신발 "별로" → **신발 카테고리 문턱이 자동 → 결재로 변경**, 이력 기록
6. **"양말 다 떨어졌어"** → 늘 사던 것, 문턱 안 → 자동 처리 영수증

## 설계 원칙
- **판정은 규칙 엔진, LLM은 해석만.** 자동/결재/반려 판정과 금액 계산은 서버 코드(`judge`)가 합니다. "결제했다/승인됐다" 같은 상태 문장은 서버가 확인한 사실로만 표시합니다.
- **근거에 출처 표시.** 캘린더/옷장/대화/추정을 구분해 보여줍니다.
- **결제는 시뮬레이션.** 실제 결제·주문은 하지 않으며 화면에 표시합니다.

## 사용한 API
- **SKT A.X K2** (OpenAI 호환 Chat Completions, JSON 모드): 요청 의도 해석 (상황, 날짜, 드레스코드, 근거)
- **OpenAI API**: A.X K2 실패 시 폴백 (`OPENAI_API_KEY`가 있을 때)
- **네이버 쇼핑 검색 API**: `NAVER_CLIENT_ID/SECRET`이 있으면 실제 상품·가격·판매처 연결, 없으면 샘플 가격(화면에 "샘플 가격" 표시)

## 실행
Node.js 20+ , 의존성 없음.
```
cp .env.example .env   # 키 입력
npm start              # http://localhost:4400
```
`.env`
```
OBA_API_KEY=        # SKT A.X K2
OPENAI_API_KEY=     # 선택
NAVER_CLIENT_ID=    # 선택
NAVER_CLIENT_SECRET=
```

## 데이터
`data/` 의 착장·옷장·캘린더·상품은 데모용 샘플입니다. 착장 데이터는 팀이 운영하는 착장 서비스의 저장 결과 형식을 본뜬 샘플이며 실제 사용자 데이터가 아닙니다.

## 한계와 다음 단계
- 실제 결제(Agentic Pay)·실제 주문 연동 없음 → SKT Agentic Pay 연동 시 결재 서류의 승인 버튼이 그대로 결제 승인 단계가 됨
- 후회 체크는 카테고리 단위 규칙 변경만 지원 → 금액·판매처 단위로 확장
- 부모님 대리 결재(요청자와 결재권자 분리), 전화·문자 채널
